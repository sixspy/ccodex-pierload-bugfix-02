# BUGFIX-17 禁放修复 · 命运说明（当日封存 2026-11-24）

## 缺陷

超重账上仍有 `开放` 挂起时，放行写口不拦，正式放行册仍插入 `已放行` 行：

- `backend/validators.py` 的 `validate_no_open_overload` 是空函数（原「BUGFIX-02 埋雷」）。
- `backend/gate_svc.py` 里对该函数的调用被整段注释掉。
- 放行页虽写「无开放超重挂起」，但只改了提示字，服务端无判据。

## 口径（两边不得混用）

正确性口径：**超重未清禁放**。以超重账 `overload_holds.status='开放'` 为准，
不以票面 `status` 单边为准。

本修复采用 **甲路径**：

> 超重挂起未闭环则放行整笔回滚，正式放行册零增。

**乙路径**（放行改落影子意图、待超重闭环后原子晋升）**未采用、未混入**。
因此对账与证明只有一本账：`gate_releases.status='已放行'`，
不存在「未晋升意图被对账当已放行」的中间态。

## 改动面（三红后）

- `validators.validate_no_open_overload`：真实查询开放挂起，命中即 409。
- `gate_svc.release_gate`：
  - 先抢闸口锁 `gate:<ticket>` 与票锁 `ticket:<ticket>`（后者串行化放行与超重开挂/闭环）；
  - 校验与写入同一笔事务，写入后再次复验开放挂起，命中则 `rollback()` 整笔回滚；
  - 失败路径由 `locks.release` 先丢弃未提交写入，再清锁并落库。
- `locks`：抢锁与争用痕独立提交，败方只记 `contention_log`，不写业务。
- `db.effective_ticket_status` / `ticket_status_view`：五页同态唯一口径；
  正式放行优先，其次超重未清，再回票面存量。
- `overload_svc`：已正式放行票不得再开挂起；闭环不把已放行票回写成 `已裁定`。
- `reconcile_svc`：对账与单票证明按同一口径给 `status` / `release_blocked`。
- 页面：总览、放行、超重、过磅、对账五页共用上面的口径字段；
  放行页列出「禁放（超重未清/旁路未闭环）」，不再只是提示字。
- `scripts/_gen_pierload_frontend.py` 同步模板，避免重新生成时复原漏洞。

## 偏离记录

- 偏航拒写：任何偏离「超重未清禁放 / 甲路径」的改法一律拒收。
